# Local control service

Start the loopback server with an operator-managed credential file:

```sh
uv run python -m asr_service.http --database data/control.sqlite --credentials /private/asr-tokens.json
```

The credential JSON maps opaque bearer secrets to `subject`, `role` and explicit
`projects` arrays. Roles are `human`, `researcher`, `supervisor`, and `viewer`.
There is no default credential, request-supplied actor, wildcard project, or
remote listener. Keep the database and credential file outside researcher mounts.
The local Python APIs are trusted operator interfaces; untrusted clients use HTTP.

Every HTTP path begins `/v1/projects/{project}`. POST bodies use JSON, with the
same keyword names as the corresponding `ControlService` method. Authorization
is `Bearer {token}`. Duplicate JSON keys, NaN and Infinity are rejected. Errors
have a stable `error` field; HTTP uses 401/403 for identity/access, 409 for stale
revisions, replay conflicts, paused admission and exhausted budgets.

| Method / suffix | Behavior |
|---|---|
| POST `contracts` | `contract_id`, `document`, `expected_revision`, `idempotency_key`; immutable publication |
| POST `runs` | `run_id`, external `experiment_id`, `contract_id`, `contract_revision`, `idempotency_key`; explicit unique mapping |
| GET `runs/{run}` | Effective contract, controls, guidance, immutable admitted trials, current dispatch states, project balances |
| POST `runs/{run}/trials` | `request_key`, `variables`, `references`, `requested_budget`; admission and dispatch intent in one transaction |
| POST `runs/{run}/commands` | `kind`, `expected_revision`, `idempotency_key`, optional `payload` |
| GET / POST `runs/{run}/findings` | Evidence-linked candidate finding revisions; publication needs `finding_id`, `expected_revision`, `idempotency_key`, `statement`, `trial_ids`, `limitations` |
| GET `events?after={seq}` | Project event replay, ordered cursor, up to 1000 records |
| POST `references/{kind}` | Trusted human/supervisor registration with `document`; registration alone grants no execution |
| GET `references/{kind}/{digest}` | Hash-verified frozen metadata |
| GET `dispatch` | Trusted inspection of queued work whose run gate is open; does not claim a lease |

Commands are `stop`, `finish`, `cancel_trial` (`payload.trial_id`), `pause`, `resume`, `quota` (`payload.state`), `guidance` (`payload.text`), and `apply_contract`
(`payload.contract_id`, `payload.revision`). The command receipt's `applied` status
means its specified gate or revision was durably applied. Pause closes new
admission and queued dispatch; it permits in-flight attempts to finish. It does
not claim that a process stopped. Stop requests termination; finish drains already
active work and cancels unstarted numerical work. Both remain pending while any
numerical attempt or runtime session is unresolved. Terminal receipts preserve
the actual result when completion wins a cancellation race. Guidance is available at the next submission
boundary; its receipt does not claim researcher acknowledgement or adoption.

The control service does not create or schedule an agent runtime. An external
owner creates its Experiment and binds the unique ID here. Bindings do not prove
that an upstream runtime exists or that its old worker has been disabled. The
trusted supervisor uses the same database through `asr_supervisor.store` for
fenced execution, reconciliation and settlement. Keep that database inaccessible
to researcher/candidate processes.

## Supported executable profile

The full required document is validated against
`contracts/research-contract.schema.json`, existing variable-policy semantics,
reference contents and local pinned source/environment hashes. It is an
executable **reference profile**, not unrestricted candidate execution.

Reference registration documents must match:

- `problem`: `profile: matpower-case118/1`, pinned `case_sha256`.
- `reference`: `profile: matpower-reference/1`, pinned `image_id`.
- `evaluation`: `profile: powerflow-independent/1`, current pinned `validator_sha256`, `tolerance_pu: 1e-7`.
- `candidate`: `profile: matpower-reference/1`, pinned `image_id`, `solver: newton_raphson`.
- `input_manifest`: `profile: matpower-case118-flat/1`, published `problem_ref` digest.

Obtain pinned values from `powerflow_lab.reference.make_request()` and register
metadata before publishing. Passing placeholder metadata cannot authorize work.
Publication verifies pinned source and package files; image availability and
container isolation are checked by the supervisor at execution.

Accepted candidate settings are case118, flat initialization, Newton reference
solver and bounded iteration count. An open method policy permits proposing other
implementations, but submission returns `capability_unavailable` until a backend
supports them. It never silently substitutes the reference solver. The frozen
`execution_request` is generated by the owning admission transaction and checked
again by the supervisor; callers cannot replace its image or command.

The implemented profile supports one researcher, one numerical attempt executing
per run, timeout at most 3600 seconds, no automatic retry, and a 100 MiB evidence
publication cap. This cap is checked on publication, not a live disk quota.
Attempts reserve exactly one attempt and their timeout in integer milliseconds;
container startup/cleanup overhead can exceed that reservation and is retained
as actual cost. Limits are project-wide; creating another run does not reset
consumption. Required finite budget dimensions are `attempts`, `execution_ms`,
`research_walltime_ms`, `turns` and `tool_executions`. The runtime supervisor
first calls `claim_runtime` (HTTP POST `runs/{run}/runtime/claim`) with an owner
and idempotency key plus `runtime_identity` containing the exact contracted
provider/model/auth/billing tuple. A mismatch is rejected; a contract changing
that tuple requires a new session before further runtime activities. This
exclusively binds one unresolved session per run and
atomically reserves its bounded walltime against the project. Another run cannot
use that reservation. A replay returns `replayed: true`; it never authorizes
launching a second process. Recover the original process before proceeding.

Before a turn/tool the supervisor calls `admit_activity` (HTTP POST
`runs/{run}/activities`) with `kind`, `idempotency_key`, `session_id`, `epoch`,
and `owner`. Issued permits consume their count even on failure. The runtime
must enforce the returned `remaining_walltime_ms` during execution. After actual
process exit, `release_runtime` (HTTP POST `runs/{run}/runtime/release`) records
`execution_exited: true` and measured `actual_walltime_ms`, settles real elapsed
session time including overrun, and releases unused reservation. Before any
provider prompt, the runtime must call `attach_runtime_process` (HTTP POST
`runs/{run}/runtime/attach`) to register its immutable host, process/group ID and
OS birth identity. Control independently verifies this identity at attachment
and independently verifies the registered group has exited before accepting normal release;
a request Boolean cannot establish exit.

After a controller crash, `reconcile_runtime` (HTTP POST
`runs/{run}/runtime/reconcile`) takes `session_id`, `expected_epoch`, new `owner`
and optional `terminate`. It fences old writers before checking the registered
OS identity. It never grants a replacement launch. Verified group exit settles
conservative elapsed session time; missing, mismatched or still-active identity
leaves the reservation held, records uncertainty and closes admission. Resume
requires explicit control after successful reconciliation. Unknown execution
retains the reservation and session identity. Setup and paused gaps
outside sessions are not billed as runtime consumption.
This service is not a provider billing interceptor.

Contracts require explicit `runtime_policy`: `provider`, `model`, `auth_mode`
(`subscription_oauth`, `subscription_cli` or `api_key`), `billing_mode`
(`subscription` or `paid_api`) and `quota_state` (`unknown`, `available`,
`rate_limited` or `exhausted`). Subscription is the selected default; unknown
provider quota permits work within local finite budgets. Rate limits/exhaustion
pause subsequent admission; the adapter reports them via the CAS `quota`
command rather than changing provider or billing mode. API billing requires
`paid_api_authorized: true` in an explicitly published human contract. No
automatic fallback to paid API mode exists. These declarations do not prove
a particular SDK can use a provider subscription; adapters must verify that.

Evidence-linked findings remain `candidate` even when a solver succeeded. They
are not independent replication reports or scientific acceptance. A negative
trial can support a finding. Independent replication and held-out evaluation
remain separate work.

Guidance begins with `delivery_status: undelivered`. The active fenced runtime
can call `ack_guidance` (HTTP POST `runs/{run}/guidance/{command_id}`) with
`session_id`, `epoch`, `owner`, `status`, `reason`, and `idempotency_key`.
Statuses are `delivered`, `adopted`, and `deferred`; deferral requires a reason.
Acknowledgements have immutable identities and events, and remain researcher
statements rather than scientific validation. A persisted guidance command does
not imply delivery or adoption.

Claims begin in `launch_state: prepared`. After credential/version preflight,
the trusted launcher calls `begin_runtime_launch` (HTTP POST
`runs/{run}/runtime/launch`) immediately before spawning the process. This issues
a single durable grant; repeating it cannot authorize another launch. Setup
failure before that grant may call `abort_runtime_prelaunch` (HTTP POST
`runs/{run}/runtime/abort-prelaunch`) with a reason to release the unused
reservation. Once a launch grant exists, absent identity remains unresolved and
cannot use this setup-failure path.

Host process receipts establish exit of the registered process group. They do
not establish containment of descendants that detach into another group; this
researcher profile exposes bounded file tools and keeps numerical execution in
the supervised container backend. Broader researcher shell privileges require
a verified OS execution boundary before claiming complete subtree containment.

## P3 hypothesis revisions (first D016 slice)

Project-scoped hypotheses are immutable author statements, independent of runtime
sessions. `publish_hypothesis(token, project, hypothesis_id, document,
expected_revision=..., idempotency_key=...)` appends a revision under a SQLite
write transaction with an event and replay receipt. The service assigns revision,
parent revision, author, timestamp and document SHA-256. A stale version or a
reused key with different content is rejected. Publication does not judge whether
an experiment is valid or a hypothesis is supported.

HTTP provides POST `/v1/projects/{project}/hypotheses` with `hypothesis_id`,
`document`, `expected_revision`, and `idempotency_key`; GET the same path lists all
revisions, and GET `/hypotheses/{hypothesis_id}` filters that list. Human and
researcher roles can publish; existing project ACLs govern reads. The strict
schema is exported as `asr_service.hypotheses.HYPOTHESIS_SCHEMA`.

The document requires nonempty `statement`, `prediction`, `scope`,
`refutation_criteria`, and `change_reason`, plus `study_type` (`exploratory` or
`confirmatory`) and `analysis_timing` (`prospective` or `post_hoc`). Unknown fields,
including author-written validation status, are rejected. Revisions form a
linear parent chain within a project/hypothesis ID; branching hypotheses and
formal Validation reports are outside this slice.

Trial admission optionally accepts:

```json
{"hypothesis_ref":{"project_id":"project-id","hypothesis_id":"hypothesis-id","revision":1}}
```

The owning transaction checks project membership and exact revision before
reserving resources, then freezes that reference with the document hash beside
the already frozen evaluation reference. Later revisions cannot replace it.
Omitting the reference preserves the historical request encoding and replay
receipt. New omitted-reference trials use the compatibility label
`legacy_unlinked`; old records receive that label only in the read projection.
Persisted trial evidence and old receipts are not rewritten.

Finding publication optionally accepts `hypothesis_evidence`, a nonempty array:

```json
[{"hypothesis_ref":{"project_id":"project-id","hypothesis_id":"hypothesis-id","revision":1},"trial_id":"trial-id","assessment":"uncertain","scope":"This fixed input only","analysis_timing":"prospective"}]
```

Assessment choices are `supports`, `opposes`, and `uncertain`. Every trial must
already belong to the finding's verified evidence list. Stored links include its
actual attempt/manifest and are explicitly marked `assessment_kind: author_claim`.
They cannot set an evaluator or formal validation state. `prospective` is accepted
only for the exact hypothesis revision frozen at trial admission and a hypothesis
not marked post hoc. Legacy unlinked trials or a different revision require an
explicit `post_hoc` interpretation; they cannot be backfilled as earlier
predictions. New finding revisions preserve prior opposing or uncertain records.
No relationship automatically establishes scientific support or refutation.

When the optional upstream AAR organization is enabled, its shared Finding
projection carries these canonical links in `config.hypothesis_evidence` and
preserves `status: candidate`. Prior finding revisions remain separate Forum
records, including opposing claims; projection consistency checks reject altered
links. This does not introduce a second Hypothesis authority in the upstream ORM.


## Evaluator Validation records

`POST /v1/projects/{project}/runs/{run}/validations` accepts
`{validation_id,document,idempotency_key,supersedes?}` only from an operator-configured
`evaluator` principal for that project. Researcher, human, supervisor and viewer
roles cannot publish these reports. `GET` on the same route returns all immutable
reports to authorized project readers. Supersession appends a new report for the
same target and retains prior negative results.

`document.target` binds trial_id, execution_attempt_id, manifest_hash and
evaluation_ref. Publication checks actual terminal execution identity, frozen
reference and current raw artifact inventory. The service computes report SHA256
and publisher identity; neither can be supplied by the caller. The six separate
assessment axes are experiment_validity, equation_validity, operating_checks,
replication, generalization and hypothesis_assessment. Invalid/unassessed
experiments cannot support/oppose hypotheses or support generalization.
Hypothesis assessments require an exact version reference and explicit
prospective/post_hoc timing; prospective requires the trial's frozen declaration.
The strict document schema lives in `asr_service/validations.py`.

`provenance` records method, execution/frozen-material/mathematical independence
observations and limits. These are evaluator attestations: the control service
verifies references and bytes, not OS containment or scientific truth. Stored
`isolation_verified_by_service` remains false. Publication does not change the
attempt's execution outcome or promote a candidate Finding. The isolated checker
must separately supply actual execution evidence; calibration reports are not
automatically migrated into independent validations.

## Logical resource ledgers

Run reads preserve the legacy flat `budget` and add `resource_ledgers`, in the
same SQLite read transaction. Model activity contains research_walltime_ms,
turns and tool_executions; compute contains attempts and execution_ms. Each
retains its own units/limit/spent/reserved/available. No aggregate monetary total
is fabricated. Unknown legacy dimensions appear under unclassified. Historical
rows remain authoritative; no migration resets or duplicates consumption.
Provider quota remains explicitly unknown here, independently of local balances
and admission state. `BudgetStore.reserve_ledgers` provides atomic reservations
across both logical groups; it is a trusted primitive, not a new public endpoint
or permission to execute unsupported backends.


## P3 candidate and managed evaluation interfaces

The explicit `octave-candidate/1` profile supplements the reference profile.
`POST candidates` accepts bounded UTF-8 `source`, `request_key`, fixed entrypoint
`candidate.m`, profile and optional snapshot reference. Control stores immutable
bytes; registration does not grant execution rights. A contract must opt in via
`execution_policy.candidate_profiles`. `max_candidate_revisions` counts distinct
methods admitted in that run, including unsuccessful trials, rather than unused
registered files. Current permission and budget checks still apply.

`POST runs/{run}/replications` accepts `request_key`, parent `trial_id` and
`requested_budget`. It admits a fresh execution of the frozen source/input under
a new identity. Incompatible current evaluation/problem/method/time policies
reject the request; they do not rewrite the original attempt.

`GET / POST runs/{run}/evaluations` lists or admits evaluation jobs. Admission
uses `request_key`, `target` (trial ID, execution attempt ID, manifest hash and
evaluation reference), and `requested_budget` with `evaluation_attempts: 1` and
finite `evaluation_ms`. These dimensions belong to the compute ledger.
`GET runs/{run}/evaluations/{id}` reads a job. Supervisor-only POST actions below
that path are `claim`, `heartbeat`, `launch`, `attach`, `uncertain`, `reconcile`,
`complete`, `abort-prelaunch` and `should-stop`; they retain owner/epoch fencing.
The concrete trusted driver is `asr_evaluation.managed.run_evaluation`.

A Validation may include `evaluation_artifact` with `evaluation_id`,
`evaluation_attempt_id` and `artifact_sha256`. Control rechecks the stored artifact,
container identity and target and rejects contradictory numerical assessments.
`evaluation_artifact_verified_by_service` records that check. The existing
`isolation_verified_by_service` remains false: verified retained container facts
are not a claim that all researcher runtimes or trusted host software are isolated.
Freeform scientific claims still require separate assessment.

`POST runs/{run}/quota-observations` accepts a sourced, timestamped observation
from a human or supervisor. Unknown/stale observations do not clear a known
blocked provider; future timestamps are bounded. Availability does not reopen
admission automatically. Local finite balances remain authoritative, and neither
quota observations nor contract replacement enable API fallback.

## Versioned research organization (P5 foundation)

GET/POST `/v1/projects/{project}/runs/{run}/organization` uses the existing bearer
and project authorization. POST fields: `kind`, `entity_id`, `expected_revision`,
`idempotency_key`, `document`. Every accepted mutation appends a revision in the
same SQLite database and an event in the existing event stream. Replay returns
its original receipt; a changed payload with the same key is rejected.

| kind | document | authority |
|---|---|---|
| policy (`entity_id=capacity`) | max_active_leads, max_active_workers (positive integers) | human |
| member (entity ID is authenticated subject) | role: organizer/lead/worker, enabled: boolean | human |
| direction | title, question, owner, status: proposed/active/paused/closed, rationale, evidence_trial_ids | organizer; Leads may propose and revise their own proposed directions |
| task | direction_id, assignee, title, instructions, status: assigned/in_progress/completed/cancelled, result, evidence_trial_ids | organizer/owning Lead assigns; assignee starts and resolves in-progress work |
| message | recipients (explicit member subjects), text, evidence_trial_ids | registered participants |

Human authority can manage organization records, but cannot fabricate an assignee's
in-progress completion acknowledgement through this API. Active tasks must resolve
before changing their direction's objective/owner, pausing/closing the direction,
or disabling/retyping the assignee. Messages are immutable. Empty evidence lists
are valid for prospective plans and nonnumerical tasks; supplied trial references
must resolve to terminal published execution identities in this run. Such links
are not independent scientific validation or a fresh file-integrity attestation.

GET query parameters: `after` (sequence cursor, default0), `limit` (default100,
maximum500). Returns `records`, `next_after`, `has_more`; reconstruct latest state
by entity/revision, follow all pages, retain earlier revisions. Team history is
shared among authorized members; recipients express intended discussion targets,
not confidentiality, automatic notification or delivery acknowledgements.

A paused research run permits discussion and in-progress result preservation,
but not new task starts/assignments or active direction changes. A closed run only
permits exact replay/read. Capacity and64KiB document failures produce durable
request_deferred events with limits, request identity/hash and recovery guidance;
no research cancellation, budget reset or automatic retry occurs.

This is a coordination record plane. Member-role ACL applies to these organization
operations; it does not retrofit role isolation onto all legacy researcher APIs.
The new bridge profile grants no numerical/evaluator operations. Task claims do
not launch processes or prove they exited. Runtime identity/budget binding and
actual multi-role AAR execution are the next slice, with the existing single-owner
runtime guard preserved meanwhile. Split/merge can be represented by new/closed
directions and rationale; atomic multi-direction lineage operations are not yet
implemented. No new model budget or autonomous-organization claim follows.
