## 0. 执行摘要

### 0.1 当前对问题的工作假设

根据目前有限的口头信息，真实卡点可能是：

- 在已有或已知的样本分布内，可以持续生成样本，并通过 AC
  潮流计算获得收敛结果；
- 当尝试向已知分布之外扩展时，样本生成变得困难，很多候选样本无法得到可用的潮流解；
- 这一问题已持续较长时间（据称约半年），曾考虑用强化学习进行主动探索，但没有形成有效方案；
- 上游希望持续获得足够丰富、有效、具有代表性的样本，供下游模型训练或研究使用；
- 手头存在一些 MATPOWER
  算例，但目前没有取得完整的算例文件、输入扰动定义、求解配置和失败日志。

以上是**工作假设，不是已经确认的正式问题定义**。尤其需要确认“样本分布”具体指什么、OOD
如何定义、失败究竟代表物理不可行还是求解器未收敛，以及下游模型的真实任务是什么。

### 0.2 本项目真正要研究的事情

不把问题简化为“让 Newton-Raphson 多收敛一些”，而是研究：

> 如何在电网运行条件空间中主动发现已知分布之外、具有物理意义且对下游任务有价值的可行运行样本；同时，如何识别并改善困难样本上的潮流求解能力。

这包含两个独立、相互反馈的研究课题：

1.  **可行域发现与样本分布扩张：**
    找到过去没有覆盖的可行运行区域，主动生成新样本。
2.  **困难潮流求解：**
    对物理上存在有效解、但现有算法难以求解的样本，研究更可靠的求解路径。

最终通过一个双层主动研究闭环连接二者，但不能把“分布外”“物理不可行”和“算法不收敛”混成同一个概念。

### 0.3 两周原型的定位

两周不是承诺解决半年未解决的全部问题，而是形成足以判断研究路线是否有希望的证据：

- 公开标准系统上可以复现已知样本分布和求解基线；
- 可以复现或借鉴 PFΔ、GridFM DataKit 等公开样本生成路线；
- 至少一种主动探索方法能在明确的 OOD 测试条件下扩大可行样本覆盖；
- 对一部分已确认可行但传统 NR
  难以求解的样本，能找到更可靠的求解策略或明确的失败机制；
- GPT/Claude
  能在受控实验环境中自主提出假设、设计实验、修改实现、分析结果并迭代；
- 所有结果可以通过固定数据、代码版本、随机种子和独立验证流程复现。

**本阶段不承诺：**
解决任意电网、任意拓扑、任意运行方式下的潮流收敛问题；证明某个样本在数学上绝对无解；替代真实业务下游训练任务；直接形成生产级求解器。

### 0.4 全 AI Coding 条件下的工期解释

本任务书原先的“两周”应理解为**带有研究验证缓冲的日历周期目标**，不是传统人工逐行编程的工时估算，也不是要求
AI 按照固定顺序完成全部工作。v2.1 已考虑 AI Coding，但 v2.2 进一步采用
AI-native 的执行方式：顶级推理/编程模型承担主要研究与实现工作，Agent
并行执行相互独立的研究方向，确定性实验环境自动运行和评价，人类主要负责专业假设确认、研究方向判断和关键结果验收。

在环境可用、IEEE-118 模型可获取、MATPOWER/Octave 或 Python

## 1.2 当前最重要的未知项

在开始大规模实现之前，应尽早向领域负责人确认以下问题：

1.  **“样本”到底是什么？**
    是负荷/发电/拓扑等输入运行场景，还是输入与潮流解组成的完整样本，还是连续时序样本？
2.  **“已知分布”如何定义？**
    来自历史运行数据、人工指定的参数范围、已有生成器，还是下游训练集？
3.  **“分布外”如何定义？**
    超出参数范围、统计分布变化、空间相关结构变化、拓扑变化，还是模型训练集未见过的场景？
4.  **“不收敛”具体是什么？** MATPOWER `runpf`
    返回不收敛、达到最大迭代次数、残差不达标、出现
    NaN/异常电压，还是得到结果但违反运行约束？
5.  **潮流模型与运行方式如何固定？** Slack 分担、发电机参与因子、PV/PQ
    转换、无功限值、变压器分接头、并联补偿、负荷模型等分别如何处理？
6.  **下游训练的真正目标是什么？**
    预测电压/潮流、近似潮流求解、状态估计、稳定性识别、运行场景生成，还是其他任务？
7.  **现有半年工作具体卡在哪里？** 是无法产生足够多的可行 OOD
    输入，还是样本能产生但标签算不出来，还是算得出来但不符合下游需要？

这些问题不应成为启动公开原型的阻塞项，但必须作为“需求澄清清单”持续维护。原型的假设不得悄悄升级为真实业务事实。

# 2. 核心问题建模：必须区分的五个空间

当前任务最容易发生的概念错误，是把
OOD、物理不可行、算法不收敛和样本无价值混为一谈。必须分别定义。

## 2.1 输入运行条件空间 Ω

输入变量可能包括：节点有功/无功负荷；发电机有功出力、无功能力、参与因子和电压设定；新能源出力及其空间相关性；线路、变压器、母线和发电机拓扑状态；变压器分接头、并联电容/电抗器等控制状态；网络参数扰动（应作为独立实验维度，不应与正常运行场景混为一谈）。

一个运行场景可抽象为：`u = (Pload, Qload, Pgen, Vset, topology, controls, parameters)`。Ω
表示允许研究的输入空间。它不是简单的单一负荷缩放区间。

## 2.2 AC 潮流方程可解集合 F_eq

对给定输入 `u`，AC 潮流方程可写成 `g(x; u) = 0`，其中 `x`
是待求状态变量，例如节点电压幅值和相角。`F_eq`
表示存在满足原始潮流方程的状态解的输入集合。

注意：一个输入可以有多个数学解；物理上存在解不代表某个具体算法从某个初值一定能找到；数值求解失败不能自动证明不存在解；非线性
AC
潮流的“无解”判断可能很困难，普通求解器未收敛只能记为未知，不能直接标成物理不可行。

## 2.3 运行约束可行集合 F_op

在潮流方程有解之外，还需要判断是否满足业务运行约束，例如节点电压上下限、线路和变压器热稳定限值、发电机有功/无功能力、备用和功率平衡、设备状态、控制策略和调度规则。

必须区分：

- **方程可解：** 存在满足 AC 潮流方程的解；
- **运行可行：** 方程有解，并且满足指定运行约束；
- **潮流结果有效但越限：** 方程残差通过，但某些运行约束违反。

对 PF 数据生成而言，运行约束越限的样本未必没有价值；对 OPF
或安全运行训练任务而言，它可能属于另一类标签。不能把“越限”直接标为“潮流无解”。

## 2.4 求解器收敛域 B(A, x0, c)

算法 `A` 在初值 `x0`、配置 `c` 下能够找到有效解的输入集合，记作
`B(A, x0, c)`。它取决于算法实现、初值策略、收敛容差、最大迭代次数、阻尼/线搜索/变量缩放、PV/PQ
转换、无功限值处理和稀疏线性方程求解器。

**不收敛是算法与配置相对于某个输入的结果，不是物理不可行的证明。**

## 2.5 下游目标分布 D_target

真正需要生成的样本分布取决于下游任务，而不是只取决于求解器能否计算。例如：潮流代理模型关注目标运行条件下的状态预测误差；收敛性预测关注求解难度与成功/失败边界；稳定性识别关注临界边界及其附近的运行状态；调度场景学习则需考虑真实运行方式、拓扑事件和时间相关性。

当前尚不知道真实下游任务。因此本阶段可以建立代理评估接口，但不得把代理指标冒充真实业务收益。

## 2.6 每个样本必须有多维标签

| 标签                 | 含义                                          |
|----------------------|-----------------------------------------------|
| `scenario_valid`     | 输入场景结构、单位、设备状态和拓扑是否有效    |
| `pf_equation_status` | 已找到有效根 / 多方法未找到 / 未知            |
| `operational_status` | 约束满足 / 存在越限 / 未评估                  |
| `solver_status`      | 求解器成功 / 失败 / 超时                      |
| `solver_config`      | 算法、初值、容差、最大迭代次数、版本          |
| `difficulty`         | 迭代次数、残差轨迹、Jacobian 指标等困难度特征 |
| `ood_group`          | 相对哪个训练分布、在哪些维度上属于 OOD        |
| `downstream_utility` | 对真实下游任务的价值；未知时必须标记未知      |

对“未找到解”应使用 `unknown` 或 `unresolved`，不能仅凭 NR 失败标记为
`infeasible`。

# 3. 研究目标与范围

## 3.1 核心研究问题

- **RQ1：可行域发现。**
  在给定电网模型和运行规则下，如何主动发现已知分布之外的 AC
  潮流可行运行条件？
- **RQ2：样本多样性。**
  如何避免样本只沿一个负荷缩放方向扩张，真正覆盖负荷空间分布、发电组合、拓扑和运行方式的变化？
- **RQ3：困难样本求解。** 对物理上有解、但标准 NR
  在常规初值下失败的样本，哪些数值方法或求解策略能够提高成功率？
- **RQ4：失败信息利用。** 能否把求解失败、残差形态、Jacobian
  病态和边界信息转化为下一轮样本搜索的指导信号？
- **RQ5：下游价值。** 新样本是否能提升真实下游任务在独立 OOD
  测试集上的表现？
- **RQ6：自动化研究。** GPT/Claude
  能否通过多方向并行探索、可复现实验和共享发现，自主找到人工预设方案之外的有效策略？

## 3.2 本阶段目标

在 IEEE-118 上建立可复现研究原型：

1.  固定原始网络模型、运行约定和求解配置；
2.  定义一个可复现的已知分布和若干明确的 OOD 测试组；
3.  建立 Random/LHS 等基础采样基线；
4.  复现 PFΔ、GridFM DataKit 中适用于 IEEE-118
    的公开生成方法或关键子流程；
5.  实现至少一种边界探索方法和一种多维主动采样方法；
6.  建立独立的潮流解验证与困难样本分类流程；
7.  通过受控自动化研究循环，探索额外策略；
8.  形成样本覆盖、求解表现、计算成本和下游价值的对照实验。

## 3.3 非目标

- 不在两周内开发完整强化学习系统；
- 不从零实现大型扩散模型；
- 不把 IEEE-118 上的结论直接外推到真实大电网；
- 不将普通求解器未收敛等同于物理无解；
- 不把 ACOPF 求解成功直接等同于指定输入的 AC PF 已经成功；
- 不在下游任务尚未明确时宣称样本已具有真实业务价值；
- 不追求单一综合分数掩盖样本覆盖与物理有效性之间的权衡。

# 4. 实验平台与确定性计算内核

## 4.1 IEEE-118 的角色

IEEE-118
用于公开原型和方法对照，不代表真实业务电网。它有公开、可复现的网络模型，可以和
PFΔ
等公开数据集对照，规模足以体现多节点非线性潮流特征，也可以在合理计算资源内执行大量实验。

## 4.2 求解器和模型的选择原则

- 由于需求方提到的真实失败案例来自 MATPOWER，**首选 MATPOWER 原始 case
  文件作为权威输入格式和第一参考求解环境**。
- 可以使用 Python 负责实验编排、采样、统计和可视化；MATPOWER 可通过
  MATLAB/Octave 或合适的封装执行。
- pandapower 可作为 Python 侧便利工具，但 MATPOWER 与 pandapower
  的网络转换、默认参数、控制和求解选项必须核对，不能假定结果天然一致。
- PowerModels.jl /
  Ipopt、pandapower、其他成熟求解器可作为交叉验证路径。它们的“成功”也必须回代原始
  AC 潮流方程验证。
- 不要一开始同时维护多个网络模型版本。先建立一个 canonical
  case，并保存转换脚本、转换前后差异和哈希。

## 4.3 必须固定的运行约定

实验配置至少明确：MATPOWER /
求解器版本；baseMVA、节点/支路/发电机数据版本；Slack
节点及有功平衡处理方式；发电机参与因子或出力调整策略；PV/PQ 类型与 Q
限值切换策略；变压器变比、相移、并联电纳和控制模型；负荷模型及 P/Q
扰动规则；初值策略、收敛容差和最大迭代次数；线路/变压器运行限值是否作为样本筛选条件。

特别注意：负荷增加时，必须明确新增有功和无功由谁承担。若未定义机组出力调整和
Slack 规则，实验可能只是在制造机组超限或功率平衡不一致的失败样本。

## 4.4 AC PF 与 AC OPF 的职责必须分开

- **AC PF：**
  给定负荷、发电机出力/电压设定和拓扑，求解电压状态及相应功率平衡量。
- **AC OPF：**
  在潮流方程和运行约束下优化发电机等控制量，寻找满足优化模型的运行点。

ACOPF
可以用于构造或筛选某些可行运行点，但它改变了控制变量的确定方式。若下游需要的是给定调度输入下的
PF 样本，应在生成 dispatch 后锁定相关设定值，再运行 AC
PF，并按目标标签定义验证。不能把“OPF 成功”直接当作“原定 PF 输入可解”。

## 4.5 计算契约

每次实验都必须产生结构化记录：

**输入：** case ID/hash、场景
ID、扰动定义、拓扑版本、机组调度规则、求解器版本、算法、初值、容差和随机种子。

**输出：** 收敛状态、终止原因、迭代次数、耗时、最大 P/Q
mismatch、残差轨迹、节点电压、支路潮流、机组出力、越限清单、数值告警及验证结果。

失败也必须保存。禁止只保存成功样本或把失败日志丢弃。

# 5. 样本空间设计与生成策略

## 5.1 不要把 OOD 简化成单一负荷系数 λ

原任务书提出已知区域 `λ ∈ [0.75, 1.00]`、扩展区域
`λ ∈ [1.00, 1.25]`，可以保留为**第一条可控实验轴**，但不能作为整个研究空间。

至少逐步考虑以下维度：

| 维度         | 变化内容                       | 需要明确的物理规则             |
|--------------|--------------------------------|--------------------------------|
| 总负荷       | 全网负荷整体缩放               | 发电平衡和备用能力             |
| 空间负荷形状 | 各区域/母线负荷比例变化        | P/Q 相关性、区域总量约束       |
| 负荷相关性   | 区域同步、反向或时序相关变化   | 相关结构来源与合理范围         |
| 发电组合     | 机组出力重新分配               | P/Q 上下限、参与因子、机组启停 |
| 新能源       | 风光出力水平和空间相关性       | 可用功率、预测误差、爬坡边界   |
| 无功支撑     | 发电机 Q、补偿装置、Vset 变化  | Q 限值、PV/PQ 转换、设备状态   |
| 拓扑         | N、N-1、N-2、指定线路/机组退出 | 孤岛、连通性、可运行拓扑筛选   |
| 控制状态     | 分接头、并联补偿、母线控制     | 离散控制逻辑及动作限制         |
| 参数扰动     | 支路 R/X、变比等变化           | 作为模型鲁棒性实验单独标记     |

首轮不必同时扰动所有维度。应采用分层实验：先单因素，再两因素组合，最后选择有意义的多因素组合，便于解释失败原因。

## 5.2 样本生成方法族

### G0：随机采样与 LHS 基线

- 均匀随机或 Latin Hypercube Sampling；
- 在固定边界内采样；
- 记录生成数、结构有效数、求解成功数和唯一有效样本数；
- 作为所有主动方法必须比较的基线。

不能只比较“收敛率”。应同时比较单位时间获得的唯一有效样本数和覆盖度。

### G1：结构化场景采样

使用区域负荷曲线、空间相关扰动、发电组合和新能源场景，生成比独立逐节点噪声更有物理意义的运行样本。若缺乏真实时序数据，先用明确的合成相关模型，并将其标注为合成分布，不得称为真实运行分布。

### G2：可行域引导采样

研究基于 OPF-Learn / PFΔ 思路的可行区域采样：

- 不是在大范围内盲目随机后只保留少量成功样本；
- 尝试利用优化模型、约束信息或可行性反馈构造更高效的候选输入分布；
- 若使用 ACOPF 产生 dispatch，必须明确其优化目标、控制变量、约束和后续
  PF 验证；
- 记录采样器覆盖范围、筛选拒绝率和生成偏差。

可行域采样方法本身可能引入偏置，不能只报告它的成功率，还要检查样本是否集中在某些局部区域。

### G3：连续潮流与边界探索（CPF）

从一个已知可行运行点出发，沿指定加载方向追踪潮流解，逐步接近电压稳定边界或求解困难区域。

- 先实现简单加载路径，再视需要实现 predictor-corrector；
- 不应只使用一个全局 λ
  方向。应尝试不同区域负荷方向、发电参与因子和拓扑条件；
- 记录步长、预测/校正误差、鼻点/转折点、PV/PQ 切换和终止原因；
- CPF
  沿某条路径得到的是边界附近的局部信息，不等于已经覆盖完整高维可行域；
- 接近边界的样本应单独分层，不要与普通运行样本混为一个分布。

### G4：多维主动采样与覆盖缺口探索

根据当前样本库，主动选择下一批候选样本。可研究：

- 特征空间覆盖缺口：优先探索样本稀疏区域；
- 新颖性/距离：选择与已有样本差异较大的候选；
- 不确定性：利用代理模型估计尚未理解的区域；
- 边界关注：优先探索可行/不可行或易收敛/难收敛的分界附近；
- 约束引导：避免明显不合理的输入组合。

候选方法可以包括 adaptive sampling、active learning、Bayesian
optimization、进化搜索等。先做简单、可解释的版本，再判断是否值得上 RL
或生成模型。

### G5：失败驱动探索

失败不是垃圾数据，而是研究信号。将失败样本按残差轨迹、失败节点、Jacobian
指标、迭代步数和数值告警聚类，寻找共同结构。然后针对失败模式提出局部扰动、改变发电参与方式、调整无功支撑或改变拓扑等候选方向，重新搜索邻近可行区域。

失败驱动探索需要区分：

- 输入数据/拓扑错误；
- 运行约束冲突或功率平衡设置不一致；
- 物理上可能不可行；
- 物理上有解但当前求解器/初值失败；
- 结果已收敛但运行约束越限。

不得把“失败样本附近的成功样本”直接当作对原失败样本的修复。必须保存扰动前后输入差异，并重新验证。

### G6：生成模型路线（后续研究）

Constrained diffusion、flow
matching、学习可行联合分布等方法可作为后续候选。前提是已经有足够可靠、覆盖多样的训练样本与独立评价集。第一阶段不建议直接从扩散模型开始，否则很容易把数据偏差和模型生成偏差混在一起。

# 6. 困难样本求解与失败机制研究

本层研究对象不是所有 OOD 样本，而是已经有证据表明 AC
潮流方程存在有效解、但某些常规求解流程难以找到解的样本。

## 6.1 求解基线

至少建立以下基线，并记录各自的初值和配置：

1.  MATPOWER 标准 Newton-Raphson，flat start；
2.  Newton-Raphson，DC 潮流热启动；
3.  Newton-Raphson，上一时刻/邻近成功样本热启动（仅在有合理邻近关系时使用）；
4.  Fast-Decoupled Power Flow；
5.  其他可获得的成熟求解器作为交叉验证。

所有算法必须使用统一的原始方程残差和物理校验标准。不能仅比较各自软件返回的
`success` 标志。

## 6.2 候选困难样本处理方法

- **多初值策略：** 从 flat start、DC
  解、邻近运行点和受控扰动初值启动；统计找到解的比例及额外计算成本。
- **阻尼 Newton / 线搜索：** 对过大的 Newton
  步长进行控制，避免迭代远离合理运行区域。
- **自适应变量缩放：** 检查变量量纲、残差尺度和 Jacobian 数值条件。
- **Continuation / Homotopy：**
  从较容易求解的问题逐步变形到目标问题，研究路径和参数步长对成功率的影响。
- **HELM：**
  作为不同数值思想的候选求解路径，重点评估适用范围、计算成本和实现成熟度。
- **故障定位：** 分析残差最大的节点、PV/PQ 切换、Q
  限值、孤岛、弱连接、Jacobian 条件性和线性方程分解告警。

AI
可以提出新的组合策略，但每次策略变化必须能通过配置和代码版本准确追踪。

## 6.3 “已确认可行但 NR 失败”的判定

这是困难求解研究的核心测试集。不能只用 NR
失败来构建它。建议采用多条独立证据：

- 另一个独立算法找到解，且解回代原始方程残差通过；
- 经过 continuation/homotopy 路径到达目标点，并通过原方程校验；
- 多个求解器对同一输入得到一致或可解释的有效解；
- 如条件允许，使用专门的可行性分析或数学证据进一步分类。

若目前只有一个求解器失败、其他方法也未找到解，应标记
`unresolved`，不能标记为 `infeasible`。

## 6.4 失败日志必须包含的证据

至少记录每轮迭代的 mismatch、步长/修正量、电压幅值范围、关键节点、PV/PQ
状态变化、Jacobian
估计条件性或分解告警、终止原因和运行耗时。日志要能支持事后分析，而不是只保存最后一行“did
not converge”。

# 7. 双层主动探索闭环

样本生成与困难求解应作为两个相互独立、又能相互反馈的研究循环。

## 7.1 Layer 1：可行域发现与样本生成

目标：找到已知分布之外的新运行条件，并生成经过验证的可行样本。

循环：

1.  读取当前样本库、已知分布定义和覆盖缺口；
2.  提出候选扰动方向（负荷空间形状、发电组合、拓扑、无功支撑等）；
3.  使用随机、可行域引导、CPF 或主动采样生成候选输入；
4.  执行结构校验、潮流计算和物理验证；
5.  评估新增样本的唯一性、覆盖贡献、运行状态和生成成本；
6.  将新样本、失败原因和边界信息写回研究记忆。

## 7.2 Layer 2：困难样本求解与算法探索

目标：针对已知可行但现有算法难以求解的样本，寻找更可靠的求解路径。

循环：

1.  从样本库选择困难样本和代表性失败模式；
2.  分析残差轨迹、初值敏感性、Jacobian 和约束切换；
3.  选择多初值、阻尼 NR、CPF、HELM 或其他候选策略；
4.  运行求解并回代原始方程验证；
5.  统计成功率、成本和适用边界；
6.  把新的困难度特征和求解结果反馈给 Layer 1。

## 7.3 双向反馈

- Layer 1 产生新的困难样本，交给 Layer 2 研究；
- Layer 2 发现某些特征与失败高度相关，反馈 Layer 1 定向搜索；
- Layer 2 找到新的求解方法后，Layer 1
  可以探索此前因求解能力不足而无法标注的区域；
- 所有样本和结论保留 provenance，不能因为算法更新而覆盖旧结果。

该闭环的价值不只是提高一个数字，而是逐步扩大“已探索、已求解、已验证”的研究前沿。

# 8. 评价体系：不能只优化一个收敛率

## 8.1 样本生成指标

- **结构有效率：**
  生成的输入中，通过数据、单位、拓扑和设备状态检查的比例。
- **方程有效样本率：** 已通过独立验证确认 AC
  潮流方程存在有效根的样本比例。对未判定样本单独报告，不得并入失败或不可行。
- **运行可行率：** 方程有效样本中，满足指定运行约束的比例。
- **唯一有效样本数：** 去重后真正新增的有效样本数量。
- **单位成本产出：** 每 CPU 小时、墙钟小时或
  API/计算预算得到的唯一有效样本数。

## 8.2 覆盖度指标

不要只报告最大 λ。至少报告：

- 各输入维度的边际分布覆盖；
- 关键维度组合的联合覆盖（例如负荷形状 × 发电组合、拓扑 × 无功支撑）；
- 特征空间分区/聚类覆盖率；
- 样本间距离、新颖性和重复率；
- 相对训练分布的距离或密度变化；
- 接近边界样本的覆盖程度。

距离度量应在有物理意义的特征空间中计算，并进行尺度归一化。不能直接把不同单位的原始变量拼接后计算欧氏距离。

## 8.3 求解器指标

- 固定初值和配置下的 NR 收敛率；
- 在独立证据确认可解样本上的求解成功率；
- 迭代次数、耗时、最大 mismatch 和残差轨迹；
- 多初值成功率及额外计算成本；
- 失败机制分类；
- 结果与独立求解器/验证器的一致性。

## 8.4 下游价值指标与最小代理任务

真实下游任务未明确之前，`downstream_gain`
不能被解释为真实业务收益。但为了避免两周原型只有样本覆盖和求解成功率、完全没有样本训练价值的证据，建议增加一个轻量、明确标注为
`proxy evaluation` 的代理任务。

### 代理任务：学习电压初值，改善 OOD 潮流求解

研究问题：

> 使用已知分布样本训练的模型，在 OOD 困难样本上预测节点电压初值；与 flat
> start、DC 热启动和邻近样本热启动相比，是否能改善后续标准 NR
> 的收敛表现？

最小实验流程：

1.  **生成带标签样本。** 对每个输入运行场景
    `u`，使用确定性潮流工具得到参考电压状态
    `x*`。保存输入、求解器版本、配置、初值、完整日志和参考解验证结果。
2.  **训练轻量预测器。**
    输入负荷、发电机设定、控制变量等场景特征，输出节点电压幅值与相角。固定拓扑的首轮实验可以先不编码拓扑；拓扑变化实验再增加支路状态等特征。
3.  **严格分组切分。**
    训练集使用已知分布；验证集用于模型选择；测试集按负荷形状族、扰动方向、发电组合或拓扑场景族整体留出，不能把同一条加载轨迹的相邻点随机拆到训练和测试两边。
4.  **比较初值策略。** 在 OOD 测试集上至少比较 flat start、DC
    热启动、邻近成功样本热启动、学习模型预测初值。各策略调用相同的 NR
    实现、容差、最大迭代次数和独立 evaluator。
5.  **验证预测初值。**
    对模型输出执行必要的边界处理和参考节点约束设置，但不得把预测值直接当作潮流解。最终仍由原始
    AC 潮流方程残差和物理校验决定结果是否有效。

对照实验至少包含：

- **Control：** 仅用已知分布样本训练初值预测器；
- **Treatment：** 用已知分布 +
  主动扩张样本训练同结构、同训练预算的预测器；
- **Test：** 未参与采样、调参和训练的 held-out OOD 场景组。

报告指标：电压幅值/相角预测误差、NR
收敛成功率、收敛样本上的迭代次数和耗时、最大 P/Q
mismatch、独立验证通过率，以及相对传统初值策略的提升和多随机种子波动。

**避免循环论证的要求：**

- 测试集参考解应尽可能通过不同求解路径或独立求解器获得，并回代原始 AC
  方程验证；
- 不能仅凭生成训练标签的同一个求解器返回 `success` 就把标签视为真值；
- 对多解情况，应明确参考解分支选择（例如高电压解），避免把不同有效根的差异误判为预测错误；
- 如果无法获得独立参考解，应将该样本标为
  `unresolved`，并说明代理任务的证据限制；
- 代理任务只能说明“样本对学习初值/辅助求解有帮助”，不能替代真实下游任务的效果证明。

### 真实下游任务接入

一旦明确真实任务，应使用独立 held-out
测试集：训练集使用原始已知分布及策略生成样本；验证集用于模型选择；测试集按场景家族、负荷轨迹或拓扑组隔离，且不向采样器和研究
Agent 暴露标签。对照组仅使用原始已知分布训练，实验组使用已知分布 +
新生成样本训练，在独立 OOD
测试组上比较真实任务指标、置信区间和多随机种子结果。

如果真实任务暂不可得，以上电压初值预测可作为首选代理任务；若时间或标签质量不允许，也可以采用电压/潮流代理预测、残差预测或收敛性分类，但必须明确标记为
`proxy evaluation`，不能宣称证明真实业务价值。

## 8.5 防止数据泄漏与指标投机

- 训练/验证/测试按场景家族、负荷轨迹、拓扑组或运行条件分组切分，不要简单随机拆散高度相似的样本；
- 测试集的输入分布和标签在可能情况下对研究 Agent 隔离；
- 不允许反复查看测试结果后针对测试集调参；
- 多随机种子报告均值和波动，不挑选最好的 seed 作为唯一结果；
- 任何 reward/score
  都要检查是否可以通过重复样本、偏置分布、放宽容差或生成容易样本来“刷分”；
- 同时报告覆盖、有效率、成本和正确性，不以单一加权分数掩盖退化。

# 9. 自动化科学研究员：以 Anthropic AAR 为基础进行领域改造

## 9.1 架构原则：复用 AAR，不另建替代系统

本项目应优先复用 Anthropic Automated Weak-to-Strong
Researcher（AAR）的研究员运行与协作架构，而不是仅模仿“多个 Agent
并行写代码”，也不是重新开发一套平行平台。

AAR 的关键机制包括：

- **Research Agents：**
  自主提出研究想法、实现代码、运行实验、分析结果并继续迭代；
- **Independent Sandboxes：**
  每个研究员拥有独立工作环境，避免直接覆盖其他研究员的代码和实验；
- **Shared Forum：**
  研究员之间发布进展、发现、问题和研究方向，促进交叉启发；
- **Codebase Storage：** 保存和共享有价值的代码快照与实现；
- **Evaluation Server：** 通过统一、独立的评价服务对候选方案进行评估；
- **Dashboard / Orchestration：**
  管理研究员、实验提交、运行状态和研究进度。

本项目的原则是：**保留 AAR
已经解决的研究协作基础设施，把改造重点放在电网领域实验环境、评价器和研究知识上。**
不应为了引入 `experiments/`、`findings/` 目录而移除或替代 AAR 的
Forum、Codebase Storage、Evaluation Server 或 Dashboard。

## 9.2 AAR 组件与电网研究组件映射

| AAR 组件                  | 电网研究中的职责         | 改造方式                                              |
|---------------------------|--------------------------|-------------------------------------------------------|
| Research Agent            | 电网科学研究员           | 保留自主研究能力，提供领域任务说明和工具              |
| Independent Sandbox       | 独立实验工作区           | 每个 Agent 独立分支、依赖环境和运行目录               |
| Shared Forum              | 研究讨论与发现传播       | 保留，用于发布进展、问题、假设和研究邀请              |
| Codebase Storage          | 算法和实验实现共享       | 保留，保存可复现代码快照及版本                        |
| Evaluation Server         | 样本、求解和代理任务评价 | 替换/扩展原任务专用评分逻辑，接入 PowerFlow evaluator |
| Dashboard / Orchestration | 研究员调度和实验监控     | 尽可能复用，展示任务、运行状态、指标和资源消耗        |
| AAR Research Loop         | 假设—实验—分析—迭代      | 保留自主性，不把研究流程写成僵硬流水线                |

AAR
原仓库中的具体模块、接口和运行方式应以实际代码为准。实施前先阅读仓库、运行最小示例、绘制组件依赖图，再决定最小改造点；禁止仅凭本任务书臆造
AAR API 或大规模重写框架。

## 9.3 PowerFlow 专用实验环境：只实现 AAR 不具备的领域能力

在 AAR 之上增加确定性的 PowerFlow Research Environment，作为 Agent
使用的领域工具层：

- MATPOWER case 读取、校验和版本化；
- 场景定义、扰动生成和样本管理；
- AC PF / CPF / OPF 等求解器适配；
- 原始方程残差和运行约束验证；
- 失败轨迹采集与困难样本分类；
- 覆盖度、样本有效率、求解表现和代理下游任务评价；
- 实验 manifest、结果存储和可复现报告。

AAR 负责“研究员如何协作和持续研究”；PowerFlow Lab
负责“电网问题如何计算、验证和评价”。两者通过清晰的工具/API 契约连接。

## 9.4 建议的研究 Agent 分工

先从 4～5 个不同研究方向开始，不建议一开始启动大量同质 Agent：

| Agent                         | 研究方向           | 主要职责                                      |
|-------------------------------|--------------------|-----------------------------------------------|
| A：Feasible-region researcher | 可行域与结构化样本 | PFΔ / OPF-Learn 思路、可行域采样、场景生成    |
| B：Boundary explorer          | 边界与 CPF         | 多方向加载路径、边界追踪、临界区域样本        |
| C：Active sampler             | 多维主动探索       | 覆盖缺口、新颖性、不确定性、失败反馈采样      |
| D：Solver researcher          | 困难样本求解       | 初值、阻尼 NR、Continuation、HELM、求解器组合 |
| E：Skeptic / evaluator        | 反证与独立验证     | 复现、消融、数据泄漏检查、指标投机检查        |

分工是研究方向，不是算法限制。每个 Agent
可以提出该方向之外的新方法，但应说明为什么偏离原方向以及如何评价。

每个 Agent 有独立
Sandbox、代码分支和实验目录。共享研究发现和代码快照，但不直接覆盖其他
Agent 的未合并工作。

## 9.5 保留 AAR 的共享 Forum：它与研究记忆不是二选一

共享 Forum 继续承担实时协作职责：

- 发布当前研究假设和实验计划；
- 分享阶段性结果和失败现象；
- 提出需要其他 Agent 复核的问题；
- 通知新发现、新代码快照和重要实验完成；
- 邀请不同方向 Agent 交叉验证或挑战结论。

Forum 是研究员之间的“交流与路由层”，不应被文件目录取代。

但聊天/论坛消息本身不应成为唯一的长期研究记忆。重要内容必须沉淀到结构化实验记录和研究发现中，并通过链接回到
Forum 讨论。

## 9.6 两层持久化研究记忆：experiments 与 findings

建议在 AAR 共享存储或其可映射的外部存储中增加两类持久化记录：

``` text
shared/
  experiments/                 # 不可变实验事实
    E-000001/
      manifest.json
      hypothesis.md
      protocol.yaml
      code_revision.txt
      input_manifest.json
      metrics.json
      logs/
      artifacts/
      conclusion.md
    E-000002/
      ...

  findings/                    # 从实验中提炼的可复用研究知识
    F-000001.md
    F-000002.md
    ...

  datasets/                    # 数据集清单、版本和内容哈希
  code_snapshots/               # 可复现代码快照索引
```

目录是逻辑组织建议。若 AAR 的 Codebase
Storage、论坛附件或外部对象存储已经提供相同能力，应映射到现有能力，不必重复造轮子。

### Experiment：不可变实验记录

每次实验至少记录：

``` yaml
experiment_id: E-000001
created_at: "2026-11-02T10:00:00+08:00"
agent_id: agent-boundary-01
research_direction: boundary_exploration

hypothesis: "多方向 CPF 比单一全局负荷缩放覆盖更多边界区域"

case:
  name: IEEE-118
  source: MATPOWER
  case_hash: "..."
  model_version: "..."

protocol:
  scenario_family: "regional_load_direction"
  generator: "cpf_multi_direction"
  solver: "MATPOWER CPF"
  solver_config: "..."
  random_seeds: [11, 23, 37]

code:
  repository: "..."
  commit: "..."
  dirty_patch_hash: null

inputs:
  dataset_manifest: "..."
  scenario_ids: ["..."]

outputs:
  metrics_file: "metrics.json"
  logs_path: "logs/"
  artifacts_path: "artifacts/"

status: completed
result_summary: "..."
limitations:
  - "仅覆盖指定加载方向"
```

实验记录应保留失败和负面结果。原始日志、输入数据和二进制产物可以存放在对象存储中，但
manifest 必须保存其路径和内容哈希。已经提交的实验记录不得被后续 Agent
静默覆盖；更正应通过新版本或补充记录完成。

### Finding：结构化研究发现

每个发现使用统一模板：

``` yaml
finding_id: F-000001
title: "多方向 CPF 在 IEEE-118 上发现额外边界区域"

status: preliminary
# candidate | preliminary | independently_reproduced
# replicated | refuted | retired

hypothesis:
  statement: "..."
  motivation: "..."

scope:
  network: "IEEE-118"
  scenario_families: ["..."]
  conditions: ["..."]

method:
  description: "..."
  key_parameters: {}

evidence:
  supporting_experiments: ["E-000001"]
  contradicting_experiments: []
  artifacts: ["..."]

result:
  observed_effect: "..."
  metrics: {}
  comparison_baseline: "..."

limitations:
  - "..."
negative_results:
  - "..."
reproducibility:
  code_revision: "..."
  data_hashes: ["..."]
  command: "..."

confidence: low
next_questions:
  - "..."

author: "agent-boundary-01"
reviewed_by: []
created_at: "2026-11-02"
```

状态必须反映证据等级：

- `candidate`：提出了假设，尚无充分实验；
- `preliminary`：有初步实验支持；
- `independently_reproduced`：由不同 Agent 或独立工作区复现；
- `replicated`：关键结论在预先定义的独立实验条件下稳定复现；
- `refuted`：证据否定原假设；
- `retired`：不再适用或被更新发现取代。

**任何 Agent
都可以发布候选发现，但不能自行把自己的发现标记为已独立复现或最终确认。**
结论状态由独立 evaluator 或复核 Agent 根据证据更新。

## 9.7 共享记忆如何与 AAR 协作

推荐采用以下协作路径：

1.  Agent 在自己的 Sandbox 中提出假设并执行实验；
2.  实验完成后，提交不可变的 `experiment` 记录和代码快照；
3.  Agent 将可复用结论整理为 `finding`；
4.  在 AAR Shared Forum 发布发现摘要、实验 ID、Finding ID 和复现邀请；
5.  其他 Agent 在各自 Sandbox 中同步/检索共享
    findings，决定是否复现、挑战或扩展；
6.  独立复现结果回写到新的 experiment，并关联原 finding；
7.  经独立验证后更新 finding 状态；
8.  AAR Codebase Storage 保存可复用实现，Evaluation Server
    保存权威评价结果。

Anthropic AAR
的经验值得借鉴：共享发现不应只依赖远程关键词检索或聊天上下文；应将已发布的研究发现同步到各
Agent 的 Sandbox，使 Agent 能自主浏览、检索和组合已有知识。

因此，**Forum、Codebase Storage、Evaluation Server 与
experiments/findings 是互补关系，不是替代关系。**

## 9.8 评价器与 reward hacking 防护

- 研究 Agent 不应拥有修改 evaluator、held-out
  测试集或物理校验规则的权限；
- Evaluation Server 独立运行，输入输出结构固定，保存 evaluator 版本；
- Agent 提交候选方案和实验 manifest，评价器从受控数据源读取并执行；
- 评分分开展示结构有效率、方程有效样本率、运行可行率、覆盖度、成本、求解成功率和代理下游收益；
- 不以一个加权总分掩盖某个关键指标退化；
- 对异常高分进行独立复现和抽样审计；
- 不允许通过降低容差、跳过约束、重复样本、挑选随机种子或污染测试集获得虚假提升；
- Agent
  可以提出新的评价指标，但新指标必须先经过人工/独立研究员审查，再加入正式
  evaluator。

# 10. AI-native 执行计划、最小可运行切片与阶段门

本节不是传统人工开发排期，而是全 AI Coding 条件下的日历时间目标。**前 24
小时必须形成最小可运行切片，约 2～3
天争取出现第一份有说服力的研究迹象，5～7 天形成可信原型，8～12
天完成主要研究闭环。** 第 13～14
天作为独立复现和不确定性缓冲，不应把两周理解成必须消耗完的固定工期。

所有时间均为日历时间目标，不是
Agent-hours。任务可以并行，但必须遵守依赖关系：没有可信的 canonical
case、运行约定和 evaluator，不得让多个 Agent
同时大量生成不可比较的实验结果。平台架构不应阻塞第一组真实潮流实验。

## 10.1 M1：前 24 小时必须交付——最小可运行切片（MRS）

目标：从 canonical IEEE-118 case
到批量潮流结果、独立残差检查和第一份基线报告，形成一个完整、可重复运行的纵向切片。

第一轮只需要五个脚本和一个配置文件：

| 文件                            | 必须完成的功能                                                    | 主要输出                           |
|---------------------------------|-------------------------------------------------------------------|------------------------------------|
| `scripts/00_env_check.py`       | 检查 Python、MATPOWER/Octave 或 pandapower 环境及版本             | `env_report.json`                  |
| `scripts/01_case_smoke.py`      | 加载 canonical IEEE-118，检查节点/支路/发电机数量，运行 base case | `base_case_result.json`            |
| `scripts/02_generate_known.py`  | 按固定随机种子生成一小批已知分布场景                              | `scenarios.parquet`                |
| `scripts/03_batch_pf.py`        | 对场景批量运行统一配置的 AC PF，保存成功和失败                    | `solver_results.parquet`、逐次日志 |
| `scripts/04_baseline_report.py` | 独立回代方程、统计收敛率/残差/迭代次数/耗时并画图                 | `summary.json`、图表、`report.md`  |

配置文件至少包括：

`configs/ieee118_baseline.yaml`

其中固定 case 来源和 hash、baseMVA、负荷扰动定义、发电平衡策略、Slack、Q
限值、PV/PQ 规则、求解器版本、初值、容差、最大迭代次数和随机种子。

建议输出目录：

``` text
results/
  baseline/
    manifest.json
    env_report.json
    base_case_result.json
    scenarios.parquet
    solver_results.parquet
    summary.json
    logs/
    convergence_by_group.png
    iterations_distribution.png
    report.md
```

### MRS 验收标准

- 一条命令可以完成环境检查、case smoke test、样本生成、批量 PF
  和基线报告；
- base case 输入与来源可追溯，case hash 固定；
- 至少生成一小批固定 seed 的场景（例如 20～50
  个，数量可按运行成本调整）；
- 每个场景都保存输入、求解配置、终止状态、耗时、迭代次数、最大 P/Q
  mismatch 和日志路径；
- 成功结果必须回代原始 AC 方程，不能只信任求解器 `success` 标志；
- 失败结果必须保留，不能从数据集中静默删除；
- 报告如实给出实测收敛率，不得为了达到 90% 而筛选样本或放宽容差。

**阶段门 G1：** MRS 可从干净环境重复运行，数据、日志和结果可追溯。若
base
case、功率平衡规则或模型语义尚未明确，应先记录阻塞，不得开始大规模主动探索。

## 10.2 M2 前置工作：第 1～2 天——公开方法调研与关键子流程复现

PFΔ 和 GridFM DataKit
是参考基线，不是本项目的前置依赖。完整复现可能受到环境、数据格式、依赖版本和求解器差异影响，因此设置时间盒：

- 先读论文和代码，画出数据生成流程及依赖关系；
- 优先复现与 IEEE-118
  相关的关键子流程，例如可行负荷空间采样、发电组合扰动、拓扑扰动或 CPF
  边界样本；
- 对 GridFM DataKit 优先检查场景生成、输入输出格式和评价接口；
- 原则上将每个项目的环境打通限制在半天左右；遇到明显阻塞，记录原因和替代方案，不要无限追依赖；
- 若完整复现成本过高，写一个方法思想清楚、参数透明的简化实现，并标记为
  `PFDelta-inspired` 或 `GridFM-inspired`，不得声称是官方实现复现；
- 公开方法复现和本项目原创主动探索分开报告。

**阶段门 G2：**
至少完成一项关键子流程复现，或形成具体阻塞记录及可运行替代基线。不能因第三方项目无法安装而阻断主线。

## 10.3 M2/M3：第 2～5 天——多维样本探索与边界搜索

- 保留 λ 负荷缩放作为单轴可控实验；
- 增加空间负荷形状和发电参与方式变化；
- 运行至少多个不同方向的 CPF 探索；
- 实现一种基于覆盖缺口、新颖性或不确定性的主动采样；
- 统计样本唯一性、覆盖度、有效率和单位成本产出；
- 对生成样本执行独立方程和物理验证。

**阶段门 G3：**
至少发现一组超出已知分布定义、且经验证有效的新样本。不能只以最大 λ
增加作为覆盖扩张的唯一证据。

## 10.4 M3：第 2～6 天——困难样本诊断与求解路线（并行开展）

建立困难样本集和失败模式分类；比较 flat start、DC
start、邻近热启动、多初值；尝试阻尼 NR、Continuation、HELM
或其他有依据的候选方法。对每个“新收敛”样本回代原始方程，并检查是否改变了原始输入问题。

**阶段门 G4：**
至少对一类困难样本形成可复现的诊断或求解改进；如果没有改进，也要得到可信的失败机制分析。

## 10.5 M3：第 4～7 天——最小代理下游任务

在 MRS 和样本标签质量允许的前提下，启动第 8.4 节的“学习电压初值、改善
OOD 潮流求解”实验：

- 先在固定 IEEE-118 拓扑上实现轻量模型；
- 对照“仅已知分布训练”与“已知分布 + 主动扩张样本训练”；
- 在按场景家族留出的 OOD 测试集上比较 flat、DC、邻近样本和学习初值；
- 所有预测初值仍由相同 NR 和独立 evaluator 验证；
- 若独立标签或训练预算不足，保留完整接口并报告未完成原因，不得制造代理收益。

该实验是样本“可能对下游有用”的初步证据，不是实际业务任务的替代证明。

## 10.6 M4：第 4～8 天——基于 AAR 的多方向自动化研究

先完成 AAR 仓库最小审阅和适配，不要从零搭建平行系统：

1.  阅读 AAR 代码和运行说明，成功启动一个原始示例；
2.  标出 Research Agent、Sandbox、Shared Forum、Codebase
    Storage、Evaluation Server 和 Dashboard 的实际模块；
3.  确认如何替换任务专用 evaluator，接入 PowerFlow Lab；
4.  将前 24 小时完成的 MRS 作为 Agent 可调用的确定性工具；
5.  先启动 1 个 Agent 完成“假设—实验—提交—评价—发布
    finding”的端到端流程；
6.  端到端跑通后，再扩展为 4～5 个方向不同的 Agent；
7.  各 Agent 使用独立 Sandbox，通过 AAR Forum 交流，通过共享
    experiments/findings 持久化研究知识；
8.  由 skeptic/evaluator Agent 独立复现候选最佳结果并检查指标投机。

**不要一开始就重写 AAR。** 如果原始 AAR
的某个模块无法直接适配，优先增加薄适配层，并记录具体原因。

## 10.7 M4：第 7～12 天——独立复现与研究结论

冻结候选最佳方法和配置；在未参与方法开发的 held-out
场景组上测试；多随机种子重复关键实验；复核数据泄漏、重复样本和物理约束；完成代理任务（若标签质量允许）；生成可复现报告、数据、代码和演示图。

**目标：** 在第 8～12
天完成主要结果的独立复现。若仍有环境、真实案例或标签质量问题，第 13～14
天作为缓冲期处理；不应为了赶日历时间而降低验证标准。

**最终阶段门 G5：**
结论必须由原始实验数据和独立复现支持。若结果不显著，应如实给出负面结论和下一步最值得验证的假设。

## 10.8 全 AI Coding 的团队组织与并行策略

### 角色配置

不要让所有 Agent 使用同一任务提示并重复探索。建议按以下角色组织：

| 角色                            | 建议模型能力                         | 责任                                                 | 权限边界                              |
|---------------------------------|--------------------------------------|------------------------------------------------------|---------------------------------------|
| Chief Researcher                | 最强推理模型                         | 维护研究问题、综合假设、决定下一轮方向、审查证据     | 不单独批准自己的关键发现              |
| Research Agents A/B/C           | 强推理与编程能力                     | 分别研究可行域、边界/主动采样、困难求解等不同方向    | 独立 Sandbox 和分支                   |
| Coding / Integration Agent      | 强代码工程能力                       | 建立 MRS、PowerFlow Lab 工具接口、集成可复用实现     | 不修改权威 evaluator 和 held-out 数据 |
| Independent Evaluator / Skeptic | 与主研究员独立的模型或确定性验证程序 | 复算候选结果、审查物理正确性、检查数据泄漏和指标投机 | 只读候选产物；不能由方案作者代替      |

不要求每个角色都使用最昂贵模型。最强模型应优先用于研究方向综合、困难诊断和关键设计；重复性代码实现、批量运行和数据整理可交给成本更低但能力足够的
Agent。

### 并行策略

- **启动阶段：** 1 个 Chief Researcher + 1 个 Coding Agent，先完成 MRS
  和
  evaluator。此时不宜启动大量并行研究员，因为模型、数据契约和评分标准尚未稳定。
- **探索阶段：** MRS 通过后，增加 2～3 个方向不同的 Research
  Agents，分别探索可行域、边界和困难求解。研究任务必须有足够独立性，避免多个
  Agent 改同一模块或重复跑同一实验。
- **系统研究阶段：** 单 Agent 端到端 AAR 闭环稳定后，扩展到 4～5
  个研究方向，并配置独立 Skeptic/Evaluator。
- **集成阶段：** 指定一个 Integration Agent
  负责合并经验证的代码，不允许多个 Agent 直接共享可写工作目录。

### 关键里程碑驱动，而非固定工时

| 目标时间     | 人类应看到的成果                            | 决策                           |
|--------------|---------------------------------------------|--------------------------------|
| 约 24 小时   | MRS 运行、基线数据和第一份报告              | 检查实验契约是否可信           |
| 约 2～3 天   | 第一组经验证的 OOD 可行样本、主动方法对照图 | 判断是否出现值得加码的研究信号 |
| 约 5～7 天   | 多维覆盖、困难样本分析和代理任务初步结果    | 决定是否扩大 Agent 数量和预算  |
| 约 8～12 天  | AAR 研究循环、独立复现和主要研究报告        | 决定进入真实 MATPOWER 案例阶段 |
| 第 13～14 天 | 仅用于缓冲、复核和外部依赖处理              | 不为赶工降低科学标准           |

### 人类研究负责人的工作方式

人类不需要逐行审查 AI 生成的所有代码，也不应频繁打断 Agent
做低层实现决策。更有效的参与方式是：

1.  在启动时确认关键物理假设、样本定义和研究目标；
2.  每个里程碑审查图表、原始实验记录和独立验证，而不只听 Agent
    的文字总结；
3.  对方向性错误及时纠偏，例如负荷增加时发电平衡规则不合理、OOD
    定义过窄、把求解器失败误判为物理无解；
4.  对有价值的研究发现决定是否投入更多 Agent 和计算预算；
5.  将真实 MATPOWER
    失败案例和真实下游目标逐步引入，判断公开原型是否触及实际难题。

**原则：人类把关研究方向和科学意义，AI 承担高频实现、实验和分析。**
人类不应成为每一轮代码修改和实验运行的串行瓶颈。

## 11.3 成功不是一个预设的单一百分比

样本分布生成问题。

Evaluation Server，而是与它们协同。若原 AAR
模块已经具备对应持久化能力，应通过适配层复用。

## 12.2 预算与并行资源策略

不要一开始就承诺花费 2 万美元。全 AI Coding
的优势是缩短工程周期、提高实验并行度，但不代表 Agent 越多、Token
越多就越接近科学突破。先测量单位 Agent-hour
的独立有效实验产出，再决定是否扩大预算。

成本主要取决于并行 Agent 数量、模型/API
调用量、上下文长度、实验运行时长、OPF/CPF 计算成本、是否需要 GPU
以及数据存储。电网数值计算本身未必是最大成本，研究 Agent
长时间自主迭代、重复阅读相同材料、重复运行无信息量实验和集成冲突也可能消耗大量预算。

建议按证据闸门分配资源：

- **Gate A：** 1 个 Chief Researcher + 1 个 Coding Agent，先完成 MRS
  和可信 evaluator；
- **Gate B：** MRS 通过后，增加 2～3 个不同方向的 Research
  Agents，开展并行探索；
- **Gate C：** 第一组主动方法结果经独立复现后，再扩大到 4～5
  个研究方向；
- **Gate D：** 只有当新增 Agent
  带来新的、可复现的研究发现，而不是重复已有实验时，才扩大模型预算和算力。

每个阶段都应记录模型/API 成本、Agent-hours、CPU/GPU
时间、有效实验数、独立发现数和复现通过率。不能只报告总花费或实验总数。

**预算决策原则：**
先花小钱证明评价器可信，再花钱扩大搜索；先证明并行研究有边际收益，再扩大
Agent 数量。2
万美元可以是后续规模化研究的预算上限讨论，不应成为第一轮原型的预设支出。

## 12.3 AI Coding Agent 的工作边界

AI
可以自主提出假设、修改研究代码、生成候选场景、调用求解器、执行实验和分析结果。以下事项必须受控：不允许静默修改
canonical case 或原始输入；不允许修改独立 evaluator、held-out
数据或验证容差来提高分数；不允许删除失败实验和负面结果；不允许把求解器未收敛写成物理无解；不允许把代理任务提升为真实业务结论；所有影响结论的改动必须有版本、配置和复现记录。

## 12.4 AAR 适配实施原则

1.  **先读后改：** 获取 AAR 原仓库，阅读
    README、启动脚本、配置和核心模块；先运行一个原始示例，记录运行环境和成功路径。
2.  **先映射后替换：** 画出 Research Agent、Sandbox、Forum、Codebase
    Storage、Evaluation Server、Dashboard 的真实代码模块和数据流。
3.  **最小改造：** 优先只替换任务专用
    evaluator、实验工具接口和领域提示词；保留原有研究员调度、独立沙箱、论坛、代码共享和监控能力。
4.  **先单 Agent 闭环：** 一个 Agent 完成提出假设、调用 PowerFlow
    Lab、提交实验、获得评价、发布 finding，再扩展多 Agent。
5.  **独立权限边界：** Agent
    可以修改自己的研究代码和候选策略，但不能修改权威
    evaluator、canonical case、held-out 测试集和物理验证规则。
6.  **不要把目录设计当成架构重写：** `experiments/`、`findings/`
    可以映射到 AAR 现有存储或外部数据库；Forum 仍负责交流，Codebase
    Storage 仍负责代码快照，Evaluation Server 仍负责权威评分。
7.  **同步研究知识：** 已发布的 findings 应定期同步到每个 Agent 的
    Sandbox，使其能够在本地自主浏览和检索；Forum 消息应链接到对应
    finding 和 experiment。
8.  **验证边际收益：** 先以单 Agent 跑通端到端，再增加不同方向的
    Agent。只有当并行研究带来更多独立、可复现发现时才扩大规模。

# 13. 风险与关键提醒

1.  **模型语义风险：** 负荷增加、Slack 平衡、机组参与和 Q
    限值没有定义好，会制造没有物理意义的失败样本。
2.  **OOD 定义风险：** 只改变 λ 会把高维分布问题简化成单轴外推。
3.  **可行性误判风险：** 求解器未收敛不能证明无解；OPF
    可行也不自动证明给定 PF 输入可解。
4.  **覆盖偏差风险：** CPF
    只沿选定路径探索；高成功率可能只是集中在容易区域。
5.  **标签泄漏风险：** 训练和测试样本若来自同一条高度相似的加载轨迹，OOD
    评估会过于乐观。
6.  **指标投机风险：** Agent
    可能通过重复样本、挑选随机种子、放宽容差或只选择容易样本来刷分。
7.  **跨工具差异风险：** MATPOWER、pandapower、PowerModels
    的模型转换和默认设置可能不同，必须保存差异并回代验证。
8.  **过早复杂化风险：**
    不要一开始就堆多智能体、RL、扩散模型。先证明评价器可信，再逐步增加研究自由度。
9.  **公开算例迁移风险：** IEEE-118
    上有效的方法不代表真实电网一定有效。拿到 MATPOWER
    实际失败算例后必须开展针对性复现。

# 14. 交给 AI Research Agent 的总任务说明

你不是一个只负责按需求写代码的普通编程代理，而是一个在确定性电网计算环境中工作的自主科学研究员。你的目标不是把某个预先指定算法实现出来，而是通过实验研究：

> 如何主动发现已知运行分布之外的 AC
> 潮流可行样本，以及如何提高困难样本上的潮流求解可靠性。

## 14.1 第一轮执行指令

拿到任务后，不要先搭建完整多 Agent
平台，也不要先实现复杂采样算法。按以下顺序开始：

1.  检查工作区、MATPOWER/Octave 或 Python 环境，并记录版本；
2.  获取并固定 canonical IEEE-118 case，计算文件 hash；
3.  运行 base case AC PF，保存输入、求解配置、输出和残差验证；
4.  创建 `configs/ieee118_baseline.yaml`；
5.  实现
    `00_env_check.py`、`01_case_smoke.py`、`02_generate_known.py`、`03_batch_pf.py`、`04_baseline_report.py`；
6.  生成 20～50 个固定 seed 的小批量已知分布场景，执行批量 PF；
7.  生成 `results/baseline/` 完整结果包，包括失败日志；
8.  报告真实测得的基线收敛率，不得为了达到预设比例筛选样本或放宽标准。

完成 MRS 后，再启动 PFΔ / GridFM
关键子流程复现和主动探索。第三方代码安装失败时，记录阻塞并使用简化实现继续推进。

## 14.2 AAR 使用要求

- 优先复用 Anthropic `automated-w2s-research` 原仓库的 Research
  Agent、Independent Sandbox、Shared Forum、Codebase Storage、Evaluation
  Server 和 Dashboard；
- 不要重写 AAR 的协作基础设施，先确认原仓库的实际模块和最小适配点；
- 先让单个 Agent 跑通 PowerFlow 实验的端到端闭环，再扩展为 4～5
  个方向不同的研究员；
- Forum 用于实时交流和发布通知；`experiments/`
  保存不可变实验事实；`findings/` 保存结构化研究知识；Codebase Storage
  保存可复用代码；Evaluation Server 执行权威评价；
- 每个 Agent 独立工作，重要发现必须有 experiment/finding
  ID、代码版本和数据 hash；
- findings 应同步到各 Agent
  Sandbox，不能只依赖聊天上下文或远程关键词搜索。

## 14.3 研究原则

1.  先核对问题定义、模型和基线，不要默认任务书中的所有假设都正确。
2.  优先做能快速证伪假设的小实验，不要为了形式完整先搭建庞大框架。
3.  对不同研究方向保持探索多样性，不要所有 Agent 都追逐同一个算法。
4.  把失败日志和负面结果当作研究资产，持续分析失败结构。
5.  区分样本结构有效、潮流方程可解、运行约束可行、求解器收敛和下游任务有价值。
6.  不允许通过修改 evaluator、测试集、容差或物理约束来制造提升。
7.  每项结论必须关联到可复现的输入、代码版本、配置、随机种子和验证记录。
8.  发现原任务书存在概念或方法问题时，应提出证据和替代实验，而不是机械执行。
9.  不把固定研究流程当作强制流水线。Agent
    可以自主选择先做文献核对、数学推导、数据诊断、快速实验或完整实现。
10. 最终报告要诚实区分已证明、初步迹象、未验证假设和失败方向。

**第一优先级：** 在前 24 小时内完成最小可运行切片，建立可信的 IEEE-118
基线。

**第二优先级：**
复现至少一条公开样本生成关键子流程，并完成多维主动探索和困难样本诊断。

**第三优先级：** 基于 AAR 跑通单 Agent 端到端研究循环，再扩展多方向
Agent，寻找人工预设方法之外的策略。

## 14.4 全 AI Coding 执行要求

本项目默认采用 AI-native 方式执行，而不是传统人工编程流程：

- 使用当前可用的顶级推理模型担任 Chief
  Researcher，负责研究综合和关键技术判断；
- 使用强 Coding Agent 快速实现 MRS、实验工具和可复现脚本；
- MRS 通过后，再启用多个独立研究 Agent 并行探索不同方向；
- 将重复性实验、批量数据整理、绘图和报告生成自动化；
- 以约 24 小时、2～3 天、5～7 天、8～12
  天作为进度目标，但每个目标必须由对应证据交付，不得只按时间汇报完成；
- 不要求每个 Agent
  使用相同模型或最高成本模型，按任务难度分配能力和成本；
- 不以 Agent 数量、代码行数、实验总次数或 Token 消耗衡量研究进展；
- 人类研究负责人主要审查物理假设、研究方向、关键图表、原始证据和独立复现结果，不承担逐行编程和每次实验的串行审批。

当时间目标与科学验证冲突时，优先保证科学验证。可以延期交付结论，不能通过放宽容差、减少测试场景或跳过独立复现来满足时间表。
